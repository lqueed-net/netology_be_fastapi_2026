# Демонстрационное FastAPI приложение

Мы разработаем демонстрационное FastAPI приложение, которое реализует CRUD для сущности "Item" (товар) с использованием асинхронной SQLAlchemy и PostgreSQL. Приложение будет построено с учётом принципов SOLID, что обеспечит модульность, тестируемость и лёгкость расширения.

Также добавлено:
- Подключение к Redis для кэширования
- Docker и docker-compose для развертывания
- Миграции базы данных с помощью Alembic

## Компоненты приложения

1. Настройка базы данных (database.py)
Создаём движок, фабрику асинхронных сессий и базовый класс для моделей.

2. Модель данных (models.py)
Определяем SQLAlchemy модели Item, Order и OrderItem.

3. Схемы Pydantic (schemas.py)
Создаём схемы для запросов (создание, обновление) и ответов.

4. Репозиторий (repositories/item.py, repositories/order.py, repositories/order_item.py)
Абстрактные классы и конкретные реализации для работы с сущностями. Репозиторий инкапсулирует все запросы к БД, что соответствует принципу единственной ответственности.

5. Сервисный слой (services.py)
Сервис содержит бизнес-логику и зависит от абстрактного репозитория (Dependency Inversion). Здесь можно добавить валидацию, расчёты, вызов внешних API и т.д.
Добавлено кэширование в Redis для метода получения всех товаров.

6. Эндпоинты FastAPI (routers/items.py, routers/items_orders.py)
Роутеры получают сессию из зависимости, создают репозитории и сервисы, затем вызывают методы сервиса.

7. Главный файл приложения (main.py)
Собираем всё вместе, подключаем роутеры и добавляем подключение к Redis.

8. Docker и docker-compose
Dockerfile для сборки приложения и docker-compose.yml для развертывания всей инфраструктуры.

9. Миграции Alembic
Настроены миграции для создания таблиц в базе данных.

## Принципы SOLID

    Single Responsibility:
- models.* – только определение моделей.
- schemas.* – только валидация ввода/вывода.
- repositories.* – только работа с БД.
- services.* – только бизнес-логика.
- routers.* – только маршрутизация HTTP.

    Open/Closed:
Классы открыты для расширения, но закрыты для модификации. Например, можно создать новый репозиторий для другого типа хранилища, не меняя сервис.

    Liskov Substitution:
Любая реализация Abstract*Repository может быть подставлена в соответствующий Service без нарушения работы сервиса.

    Interface Segregation:
Интерфейсы Abstract*Repository содержат только необходимые методы для работы с соответствующими сущностями.

    Dependency Inversion:
Сервисы зависят от абстракций Abstract*Repository, а не от конкретных классов. Репозитории передаются через конструктор (DI).
